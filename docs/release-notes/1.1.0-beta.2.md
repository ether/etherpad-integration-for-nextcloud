Second beta release for 1.1.0. A pad now lives as long as its file: the trash keeps it, and it goes when the file is deleted for good. Pads Etherpad has lost come back from the content saved in their files, external pads and public links are harder to misuse, and Etherpad sessions end with the access they came from.

## Highlights

* **The trash keeps a pad.** A `.pad` file in the trash keeps its pad and its history, and a restore gives the same pad back. Moving a file to the trash, through WebDAV too, no longer loses what was written since its last sync. The pad is deleted once the file is deleted for good - from the trash, past it, with a folder, or with the account - by a background job within minutes. `docs/deleting-pads.md` says what each way of deleting a file does.
* **Lost pads come back from their files.** When Etherpad no longer has a pad, opening its file says so instead of showing an empty pad, and whoever may edit the file makes a new pad from the content saved in it. A file restored from the trash whose pad is lost gets the new pad at once.
* **Pads of vanished files.** Files removed outside Nextcloud leave their pads behind. The admin page lists them, and an administrator can delete them, one or all, or forget a public one.
* **Safer external pads and public links.** Whether an external pad's server is public is decided on its address alone, the same on every PHP version, and the fetch stays pinned to that address through a proxy. Opening a public link is rate-limited and reuses its Etherpad session instead of making a new one each time, and every visitor of a writable link is an Etherpad author of their own.
* **Sessions end with access.** Deleting a protected pad's file revokes all of its Etherpad sessions, in the background where Etherpad is slow, and a deleted account loses its sessions as on a logout.
* **Groups.** Where the app is enabled for some groups only, users outside them can no longer create pads, from the "New" menu or otherwise.

## Before and after upgrading

* Nextcloud 32.0.9 is now the minimum; Nextcloud 33 and 34 remain supported.
* The setting `delete_on_trash` is now `delete_pad_with_file` and decides whether a file deleted for good takes its pad along. The upgrade takes over its value.
* If you saved the admin settings while external pads were switched off, check the external pad allowlist: that save emptied it, and an empty list admits every public HTTPS host.
* The admin endpoint `retry-pending-deletes` is now `settle-pending`. `POST /api/v1/pads/trash`, `POST /api/v1/pads/restore` and the debug endpoint `POST /api/v1/admin/test-fault` are removed.
* Pages that embed the create page: `epnc:create-failed` with `reason: 'network'` now means that no answer came and the outcome is unknown, and the event carries the server's `code` and `retryable`.
* On Nextcloud 34, the pads of the files in a folder deleted for good, and in a trash emptied as a whole, stay until a Nextcloud 34 release has the fix Nextcloud 35.0.1 has; the consistency check lists them.

## Further changes

* The last edits before leaving a pad reach its file, and two tabs syncing the same file no longer write the older revision over the newer.
* Errors are translated, say when trying again may help, and the Viewer and the embed page offer "Try again" there.
* Opening a protected pad keeps the cookies Nextcloud sets in the same answer, so a public link's first visit gets its Nextcloud session.
* Several admin settings fixes: the connection test before the first save, a trusted embed origin with `:443`, and the detected Etherpad API version.
* Credentials and pad text stay out of the exception traces Nextcloud writes to its log.
* DOMPurify updated to 3.4.17.
* CI now runs the lifecycle cases with team folders on every supported Nextcloud major, mutation-tests every change, and upgrades the last release for every new one.
