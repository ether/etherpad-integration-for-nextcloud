Second beta release for 1.1.0. A pad now lives as long as its file: the trash keeps it, and it goes when the file is deleted for good. Pads Etherpad has lost come back from the content saved in their files, external pads and public links are harder to misuse, and Etherpad sessions end with the access they came from. Beside these, the release fixes a great many smaller bugs.

## Highlights

* **The trash keeps a pad.** A `.pad` file in the trash keeps its pad and its history, and a restore gives the same pad back. Moving a file to the trash, through WebDAV too, no longer loses what was written since its last sync. The pad is deleted once the file is deleted for good - from the trash, past it, with a folder, or with the account - by a background job within minutes. `docs/deleting-pads.md` says what each way of deleting a file does.
* **Lost pads come back from their files.** When Etherpad no longer has a pad, opening its file says so instead of showing an empty pad, and whoever may edit the file makes a new pad from the content saved in it. A file restored from the trash whose pad is lost gets the new pad at once.
* **Pads of vanished files.** Files removed outside Nextcloud leave their pads behind. The admin page lists them, and an administrator can delete them, one or all, or forget a public one.
* **Safer external pads and public links.** Whether an external pad's server is public is decided on its address alone, the same on every PHP version, and the fetch stays pinned to that address through a proxy. Opening a public link is rate-limited and reuses its Etherpad session instead of making a new one each time, and every visitor of a writable link is an Etherpad author of their own, up to 250 per link and hour.
* **Sessions end with access.** Deleting a protected pad's file revokes all of its Etherpad sessions, in the background where Etherpad is slow, and a deleted account loses its sessions as on a logout.
* **Groups.** Where the app is enabled for some groups only, users outside them can no longer create pads, from the "New" menu or otherwise.

## Upgrade

* Supported are Nextcloud 32.0.9 to 34 and PHP 8.1 to 8.5; Nextcloud 35 is not supported yet. On an older Nextcloud, upgrade Nextcloud first, with the version of the app you have, and the app after it.
* Back up the database first: the update changes the app's table.
* Replace the app's directory - `apps/etherpad_nextcloud` in most installations - with the `etherpad_nextcloud/` directory of the archive, and run `php occ upgrade`, or start the update Nextcloud then offers in the browser. That runs the app's database migration: it carries the app's rows and its setting over to a trash that keeps pads (see below), adds an index, and removes the three background jobs of the old trash and the `test_fault` setting. Disabling and enabling the app, as the README describes, runs the same migration.

## Changes

* The setting `delete_on_trash` is now `delete_pad_with_file` and decides whether a file deleted for good takes its pad along. The upgrade takes over its value.
* A background job deletes the pads of files deleted for good. It runs with Nextcloud's background jobs - on every tick of a five-minute system cron, with AJAX or webcron only as often as those run - and takes a pad about five to ten minutes after its file was deleted for good; "Check pending pads" on the admin page does it at once.
* Files in the trash when you upgrade: with `delete_on_trash` on, its default, 1.1.0-beta.1 deleted a pad when its file went to the trash, so such a file, restored, gets a new pad made from the snapshot saved in it - its content, not the pad's history. With it off, and where 1.1.0-beta.1 could not delete the pad because Etherpad did not answer, the file keeps its pad and gets it back.
* Pads 1.1.0-beta.1 left behind when their files were deleted for good - with `delete_on_trash` off, past the trash, inside a folder, after a rename, or with their account - show after the upgrade as pads of vanished files on the admin page, where they can be deleted.
* If you saved the admin settings while external pads were switched off, check the external pad allowlist: that save emptied it, and an empty list admits every public HTTPS host.
* Scripts against the admin API: `retry-pending-deletes` is now `settle-pending`; the connection test no longer answers `pad_count`, and a failed test answers 200 with `ok: false`; the consistency check answers `vanished_file_count` instead of `binding_without_file_count` and `samples.bindings_without_file`. `POST /api/v1/pads/trash`, `POST /api/v1/pads/restore` and the debug endpoint `POST /api/v1/admin/test-fault` are removed.
* Other API callers: a file id has to be a positive integer, so ids such as `1e3` or `7.5` are refused, and `POST /api/v1/pads/sync/{fileId}` answers 403 to a user who may not change the file, where a reader got 200 `unchanged` or a 500.
* Pages that embed the create page: `epnc:create-failed` with `reason: 'network'` now means that no answer came and the outcome is unknown, and the event carries the server's `code` and `retryable`.
* On Nextcloud 34, the pads of the files in a folder deleted for good, and in a trash emptied as a whole, stay until a Nextcloud 34 release has the fix Nextcloud 35.0.1 has; the consistency check lists them.
* Public links count their visitors and keep their Etherpad sessions in Nextcloud's memory cache. With a local cache alone that holds for each web server on its own; without any, every open makes a session and all visitors share one author, as before.

## Further changes

* The last edits before leaving a pad reach its file, and two tabs syncing the same file no longer write the older revision over the newer.
* Errors are translated, say when trying again may help, and the Viewer and the embed page offer "Try again" there.
* Opening a protected pad keeps the cookies Nextcloud sets in the same answer, so a public link's first visit gets its Nextcloud session.
* Several admin settings fixes: the connection test before the first save, a trusted embed origin with `:443`, and the detected Etherpad API version.
* Credentials and pad text stay out of the exception traces Nextcloud writes to its log.
* DOMPurify updated to 3.4.17.
* The lifecycle cases of the trash and of team folders run against a real Nextcloud and Etherpad - the folder cases not on Nextcloud 34 before the fix above - every change is mutation-tested, and each release is upgraded from the last one on every supported major.
