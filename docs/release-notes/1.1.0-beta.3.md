Third beta release for 1.1.0. This beta adds Nextcloud 35 support, tightens checks on pad bindings and Ownpad imports, extends session revocation, and reduces duplicate work from open viewers. It also fixes many smaller bugs.

## Highlights

* **Nextcloud 35.** The app now runs on Nextcloud 35.
* **Local pad metadata comes from its binding.** The details the app reports for a file's pad on this server come from the file's binding, not from the text in the file, so a copy no longer reports the original's pad. Opening or syncing a bound file refuses metadata that names a different pad. The Ownpad import refuses pad ids that Etherpad rewrites before it acts, such as ids with spaces or `:`: through such an id, deleting one file for good could take down the public pad of another. It reads a shortcut's address only from its `[InternetShortcut]` section.
* **Sessions end for large folders too.** Deleting a folder with more than 100 protected pads, or deleting files for good where no delete request reached their pads, left their Etherpad sessions valid for up to six hours. Background jobs now revoke them.
* **Less load from open viewers.** Timed syncs of the same file are coordinated through Nextcloud's memory cache, reducing duplicate reads and writes. MIME repairs no longer scan the whole file cache on every app update or `occ maintenance:repair` run.
* **Safer pages and logs.** The page that creates a pad for an embedding site works only inside a frame, so a link alone can no longer create a file in someone's account. The external pad allowlist no longer opens frames. Accounts outside the groups the app is limited to no longer load its viewer. Pad addresses, which give access to a pad, stay out of the exception traces Nextcloud logs.

## Upgrade

Follow the [upgrade instructions in the README](https://github.com/ether/etherpad-integration-for-nextcloud/blob/v1.1.0-beta.3/README.md#upgrade), and check its requirements for your Nextcloud version. After upgrading, check the Etherpad API URL field (see Changes).

If you are also upgrading to Nextcloud 35, upgrade the app first. If Nextcloud 35 has already disabled the old version, install the new version and enable the app to run its update. Disabling removes any group restriction, so specify the groups again with `--groups` when re-enabling.

## Changes

* **The API URL field follows the Base URL.** An empty "Etherpad API URL" no longer stores a copy of the Base URL, so the API follows a later change of it. Earlier versions stored that copy. While it matches the Base URL, the form shows the field empty and the next save clears it. A copy of a Base URL that has moved since, through `occ` or the form, reads as an address of its own and is kept: check the field after the upgrade.
* **Frames.** `external_pad_allowlist` only decides which hosts the app fetches from. An Etherpad of your own that redirects to another host loses its frame where that host was allowed only through the allowlist. An Etherpad under a path can now be framed.
* **External pads.** With `allow_external_pads` on, a file bound to a pad on this server whose text names a pad on another server is refused on open, live content and sync, instead of following the text; the sync writes nothing into it. Only such installations are affected. An older version of the file, or a new external file, is the way out.
* **New pads require setup.** Without a saved Etherpad Base URL, "New pad" offers only the external tile when external pads are enabled. A picker create that encounters missing API settings attempts to remove its new file only if it is unchanged.
* **Imported Ownpad pads.** Imported public pads with IDs outside the app's `nc-…` and `r-…` formats remain in Etherpad when their files are deleted for good. Only their bindings are removed. The consistency check offers only "Forget" for them.
* **Files restored outside Nextcloud.** Files restored without their original Nextcloud file-cache entries receive new IDs when scanned. Their pads can then appear as pads of vanished files on the admin page. Do not delete those pads: they may contain newer content than the restored files. Reconnecting them is not included in this beta.
* **API callers.** `open`, `open-by-id` and `meta-by-id` return an empty `pad_id` to readers of local public pads. `initialize` does the same when it returns `already_initialized`. Metadata lookups and `resolve` leave local pad fields empty for copies and unbound files. A timed sync sent with `periodic=1` may answer 200 with `status=deferred`. `/embed/create-by-parent/{parentFolderId}` creates a pad only inside a frame; opened on its own, it shows an error. A legacy shortcut to a pad whose other file was deleted for good answers `409 legacy_collision_no_access` until that file's binding is gone.

## Further changes

* The connection test recognises a rejected API key by Etherpad's own answer, and points to proxies and firewalls in front when a 401, 403 or 407 comes without it.
* The log tells a rejected API key, missing settings and an outage apart, and the sweep warns about a pad that has waited an hour or more for Etherpad.
* Creating a pad from a template, through the external tile or by an Ownpad migration writes the file by its id and leaves a file written meanwhile in place.
* The app's old public link works without pretty URLs.
* A display name such as `/..` in a template path, and characters the admin forbade, no longer break a create.
* The restore card offers "Open the original" only for a file the user can read.
* For signed-in readers, a public pad whose read-only address Etherpad cannot give fails to open with the error card, as through its public link.
* `docs/architecture.md` says what requests, viewers, deletes and jobs cost at scale, and `tests/load/` measures it.
